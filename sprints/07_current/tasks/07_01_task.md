# Task 07_01: Beginner walkthrough with a real person, a repeatable browser walk, and the fixes (carried over from 06_12)

**Sprint:** 07     **Depends on:** none     **Size:** M
**Concepts to read first:** [07_06](../concepts/07_06_explaining-performance-numbers-and-charts-to-beginners.md)

## Goal
Someone who did not build MarketLab follows the 14-step learning walkthrough without help, every hesitation is fixed or recorded, and the browser walk becomes a script in the repository that anyone can rerun, including a keyboard-only pass.

## Context
Carried over from Sprint 06 (`sprints/06_done/pending/06_P01`): the person-tested walkthrough, keyboard-only steps 3 to 9 and the screen-reader check were not done. The Strategy Lab (this sprint) reuses the same words, tour and design system, so confusing wording found now is fixed once. Carried-over task: **06_12, acceptance item "a person who did not build the app has followed the walkthrough"**.

## What to do
1. Ask one person who has never seen the app (the owner may choose a friend or colleague; the owner may take this role only if they have not read the code) to follow `docs/02-domain/learning-walkthrough.md` with no help from the implementer. The implementer only observes and writes down.
2. Record per step in `docs/02-domain/learning-walkthrough.md` (new section "Run by a person who did not build it, <date>"): pass/fail, time taken, what the person said or did when stuck, and any word they did not understand. Do not coach.
3. Turn every hesitation into a fix (wording in `apps/web/src/copy`, layout, an added word in `apps/api/seed/learning-terms.json`) or a `pending/` item with a reason. Re-run the copy and component tests after each wording fix.
4. Add the repeatable browser walk to the repository: `apps/web/scripts/walk.mjs` using `puppeteer-core` (dev dependency, exact version at least two weeks old) and the system's Microsoft Edge or Chrome (path from the environment variable `BROWSER_PATH`, with the usual Windows locations as defaults). It performs the 14 steps against the running stack, prints pass/fail per step, saves screenshots under `data/reports/walk/` (git-ignored) and exits non-zero on any failure. It creates its own throwaway learner name each run.
5. Add a **keyboard-only mode** (`--keyboard`) that completes steps 2 to 9 using only Tab, Shift+Tab, Enter, Space, arrow keys and typing (no mouse clicks) and fails if a control cannot be reached or operated.
6. Run an accessibility-tree pass: in the same script, read the browser's accessibility snapshot of the episode screen and the score screen and assert that every interactive element has a name and that the chart and calibration plot expose their text alternatives. State plainly that this is not a screen-reader test; if a screen reader (NVDA is free) is available, have the person or the implementer listen to the score screen once and write what was read out.
7. Record the results in the completion note.

## Where to do it
- Folder / file: `docs/02-domain/learning-walkthrough.md`, `apps/web/scripts/walk.mjs`, `apps/web/package.json` (script `walk`), `apps/web/src/copy/*` for fixes.
- Technology: `puppeteer-core`, Microsoft Edge/Chrome, existing stack.
- Database schema/ownership: none (the walk creates throwaway learners and episodes in the real database; list their count in the note).

## Inputs
- The running stack (three processes), the walkthrough document, a willing person.

## Deliverables
- Filled-in walkthrough record, fixes, `walk.mjs` with the keyboard mode, completion note.

## Acceptance criteria / tests
- [ ] The person-run section exists with a result for each of the 14 steps and the person's name is not required (initials or "tester 1" is fine). All steps pass, or each failure and hesitation is fixed or listed in `pending/` with a reason.
- [ ] `npm run walk` passes all 14 steps on the running stack; `npm run walk -- --keyboard` passes steps 2 to 9 without any mouse click (the script fails if it ever calls `click` on an element in this mode: negative test by making the script count clicks and assert 0).
- [ ] A deliberate break (for example a button without an accessible name added in a temporary branch) makes the accessibility-tree pass fail (negative test, then revert).
- [ ] Copy tests (reading ease 60 or more, sentences up to 25 words) and all web tests still pass after the wording fixes.
- [ ] No secret or learner data is committed; screenshots stay under `data/` (git-ignored).
- [ ] Standing invariant: reproducibility (the script is deterministic apart from the throwaway names; it states the browser path it used).

## Out of scope
- Writing lessons, redesigning screens beyond the fixes, load testing.

## Notes for the implementer
If no person is available, do not mark the person-run item done: write the walkthrough request in `pending/` and finish the script work. The point is what a stranger trips over, not whether the steps can be completed.
