# Task 08_01: Person-run walkthrough, screen-reader pass and fixes (carried over from 07_01)

**Sprint:** 08     **Depends on:** none     **Size:** M
**Concepts to read first:** [08_06](../concepts/08_06_testing-accessibility-keyboard-accessibility-tree-and-screen-readers.md)

## Goal
One person who did not build MarketLab has followed the learning walkthrough and the Strategy Lab steps without help, someone has listened to the score screen and a Lab result with a screen reader, and every hesitation is fixed or listed with a reason.

## Context
Carried over from Sprint 07 task 07_01 (and, before it, Sprint 06 task 06_12): the scripted walks pass (14/14, keyboard-only with 0 clicks, Lab 11/11), but no stranger has used the app, and the interface was redesigned in Sprint 07. Lessons (this sprint) reuse the same words, so confusing wording found now is fixed once. See `sprints/07_done/pending/07_P01`.

## What to do
1. Ask one person who has never seen the app (a friend or colleague; the owner only if they have not read the code) to follow `docs/02-domain/learning-walkthrough.md` and then the 8 Lab steps (pick a stock, start a study, run a rule, read the cards, run a second rule, open the vault) with no help. The implementer only observes and writes.
2. Record per step in the walkthrough document (new section "Run by a person who did not build it, <date>"): pass or fail, time taken, what the person said or did when stuck, any word they did not understand. Initials or "tester 1" is enough.
3. Install the free NVDA screen reader (https://download.nvaccess.org/documentation/userGuide.html) and listen to: the sign-in form, the episode screen, the score screen and one Lab result (cards, cost table, the chart's table alternative, the vault dialog). Write what was read out and what was confusing or missing.
4. Turn every hesitation or reading problem into a fix (wording in `apps/web/src/copy`, markup, labels, a glossary term) or a `pending/` item with a reason. Re-run the copy tests, web tests and `npm run walk` (all four modes) after each fix.
5. Record the results in the completion note, including how many people took part and how long it took.

## Where to do it
- Folder / file: `docs/02-domain/learning-walkthrough.md`, `apps/web/src/copy/*`, `apps/web/src/**` for fixes.
- Technology: NVDA (Windows), the existing walk script.
- Database schema/ownership: none (the person creates a throwaway learner).

## Inputs
- The running stack, the walkthrough document, a willing person, NVDA.

## Deliverables
- A filled-in person-run section, a screen-reader section, fixes and `pending/` items, a completion note.

## Acceptance criteria / tests
- [ ] The person-run section lists a result for every walkthrough step and every Lab step; failures and hesitations are fixed or listed with a reason.
- [ ] The screen-reader section says which screens were listened to, by whom, and what was found; if no screen reader could be used, the task is marked partial and says so (do not claim it).
- [ ] After the fixes: web tests, copy tests and all four walk modes pass.
- [ ] Negative check: one fix is shown to be needed by a test or script that failed before it (for example a missing label caught by the accessibility-tree check).
- [ ] Standing invariants: reproducibility (the walk script still prints the browser path and creates its own learner).

## Out of scope
- New lessons (08_02), redesign beyond the fixes, load testing.

## Notes for the implementer
If no person is available, do not mark the person-run item done: leave it in `pending/` and finish the rest of the sprint. A stranger's confusion matters more than a passing script.
