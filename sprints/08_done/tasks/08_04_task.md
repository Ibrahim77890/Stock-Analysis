# Task 08_04: Durable rate limiter and request trace in PostgreSQL (carried over from 06_P02 and 07_P02)

**Sprint:** 08     **Depends on:** none     **Size:** M
**Concepts to read first:** [08_04](../concepts/08_04_durable-rate-limiting-and-request-logs-in-postgresql.md)

## Goal
Login, Lab and lesson limits and the "my recent requests" trace survive a gateway restart and cannot be passed by two simultaneous requests.

## Context
`RateLimiter` (in-memory, `apps/api/src/auth/auth.service.ts`) and `TraceService` (in-memory) are the two open items named in `sprints/06_done/pending/06_P02` and `sprints/07_done/pending/07_P02`. Redis is excluded by the project rules; PostgreSQL is enough for one machine.

## What to do
1. Migration: `app.rate_event(id identity PK, key text, kind text, at timestamptz default now())` with index `(key, kind, at)`; `app.request_log(id identity PK, learner_id uuid FK CASCADE null, at timestamptz, method text, route text, status int, duration_ms real, upstream jsonb)` with index `(learner_id, at desc)`. Up and down.
2. A `DbRateLimiter` with the same `allow(key)` and `retryAfterSeconds(key)` behaviour as `RateLimiter`, one atomic statement per check (count rows in the last 60 seconds for `(key, kind)` and insert only if below the limit, serialised per key with a transaction-level advisory lock or an `INSERT ... SELECT ... WHERE`). Refused calls are not stored. A cleanup (`DELETE` older than 10 minutes) runs at most once a minute and on start.
3. Move the login limiter, the Lab runs and vault limiters and the lesson-answer limiter to it (the in-memory class stays for unit tests of the interface).
4. A `DbTraceService`: store route patterns, status, duration and upstream timings (never ids, bodies or tokens), keep the last 200 rows per learner (trim on write), and serve `GET /trace` from the table.
5. Measure the added latency (p50 and p95, 200 calls each, with and without the database limiter and trace) and write it to `docs/03-benchmarks/benchmark-04-durable-limits-overhead.md`. No target before measuring.

## Where to do it
- Folder / file: `apps/api/migrations/`, `apps/api/src/auth/`, `apps/api/src/trace/`, `apps/api/src/lab/lab.service.ts`, `apps/api/test/durable.spec.ts`, `apps/api/scripts/` (benchmark).
- Technology: NestJS, `pg`, Vitest.
- Database schema/ownership: `app.rate_event`, `app.request_log` (gateway).

## Inputs
- The existing limiter and trace tests (Sprint 06 and 07).

## Deliverables
- Migration, durable limiter and trace, updated modules, tests, benchmark note.

## Acceptance criteria / tests
- [ ] Migration up, down, up.
- [ ] **Restart test:** an app instance is closed and a new one started on the same database; the new instance still refuses the 21st Lab run of the same minute with a correct `Retry-After` and still lists the earlier trace rows.
- [ ] **Concurrency test:** 30 simultaneous requests with a limit of 20 let exactly 20 through (repeat 5 times).
- [ ] Refused requests are not counted (a client in a loop recovers after the window).
- [ ] Cleanup removes rows older than the window; the trace keeps at most 200 rows per learner.
- [ ] **Negative:** the trace table never contains a learner id in the route text, a body or a token (scan after a full run of the existing specs).
- [ ] All Sprint 06 and 07 gateway tests still pass.
- [ ] Standing invariants: idempotency (cleanup twice changes nothing), reconciliation (rows counted per key equal the number accepted), reproducibility of the benchmark script.

## Benchmark
- Added latency per request (p50 and p95, 200 sequential calls to `GET /lab/studies` and `POST /auth/login`-free routes), machine details, in `benchmark-04-durable-limits-overhead.md`.

## Out of scope
- Redis, per-IP limits behind proxies, an admin screen for the logs.

## Notes for the implementer
Keep the old class for tests that need a fake clock; do not change the public limits (5 logins, 20 Lab runs, 3 vault tries per minute).
