# Task 08_07: Cross-layer checks for lessons and durable limits

**Sprint:** 08     **Depends on:** 08_03, 08_04, 08_06     **Size:** L
**Concepts to read first:** [08_02](../concepts/08_02_content-as-data-lesson-schemas-validation-and-versioning.md), [08_03](../concepts/08_03_checking-answers-on-the-server-and-idempotent-progress.md), [08_04](../concepts/08_04_durable-rate-limiting-and-request-logs-in-postgresql.md), [08_05](../concepts/08_05_explorable-explanations-small-demos-that-teach-one-idea.md), [08_06](../concepts/08_06_testing-accessibility-keyboard-accessibility-tree-and-screen-readers.md)

## Goal
On the real stack and the real database, show that the answer key never reaches the browser, progress is idempotent and private, limits survive restarts, every reply matches its contract, and a person using only the keyboard can finish a lesson.

## Context
Sprints 06 and 07 proved the same kinds of property for episodes and studies (leak fuzz, isolation, contracts, browser walks). Lessons add an answer key that must stay hidden; the durable limiter adds state that must stay correct.

## What to do
1. **Answer-key leak fuzz (real stack):** for all six lessons call every lesson route, answer every question with every option (in a random order, across several learners), and scan every reply body, error body and header for `correct`, `why` of an option other than the chosen one, and the correct index before the rule allows it.
2. **Idempotency under concurrency (real stack):** 20 concurrent identical answers and 20 concurrent "mark read" calls: one progress row each, 20 attempts recorded for answers.
3. **Isolation fuzz:** two learners, 200 random cross-access attempts on lesson routes: identical 404 bodies, no progress visible across learners.
4. **Durable limits on the real stack:** restart the gateway process between two Lab runs inside one minute and show the limit still applies; 30 concurrent answer calls with the limit 20 let exactly 20 through.
5. **Contract validation:** validate real replies of every lesson route against the gateway OpenAPI with Ajv; a deliberate field rename fails (negative).
6. **Re-seed test:** seed a lesson with a changed question and a higher version; earlier attempts keep their old version and verdicts; old progress rows are kept.
7. **Browser walk `--lessons`** (extend `apps/web/scripts/walk.mjs`): sign up, open the path, read lesson 2 step by step with a demo, answer a question wrongly and then rightly, mark the lesson done, follow the practice link; plus a keyboard-only variant (`--lessons --keyboard`, 0 clicks) and accessibility-tree assertions on the path and lesson pages. Also scan the visible text for the words score, rank, points and level.
8. **Readability and structure:** re-run the lesson content checks against the seeded database rows (not just the files).
9. **Latency:** p50, p95 and max over 100 calls each for `GET /lessons`, `GET /lessons/:slug` and an answer, direct database reads versus through the gateway, into `docs/03-benchmarks/benchmark-05-lessons-latency.md` (machine details; no target first).
10. Count and list the test learners and rows left behind.

## Where to do it
- Folder / file: `apps/api/test/lessons-e2e.spec.ts`, `apps/api/test/durable-e2e.spec.ts`, `apps/web/scripts/walk.mjs`, `apps/api/scripts/` (latency), `docs/03-benchmarks/`.
- Technology: Vitest, Ajv, Supertest, `puppeteer-core`.
- Database schema/ownership: the throwaway test database for the spec runs; the real database for the browser walk and the latency script.

## Inputs
- The running stack, the lesson seed, the Sprint 07 real-stack spec pattern (`lab-e2e.spec.ts`).

## Deliverables
- Specs, walk modes, benchmark note, completion note with counts and findings.

## Acceptance criteria / tests
- [ ] Leak fuzz finds nothing across all lessons and options; a planted leak (a test build that adds `correct` to a question reply) is detected by the same scan (negative).
- [ ] Concurrency tests leave exactly one progress row per key and the expected number of attempts.
- [ ] Isolation fuzz: 200 of 200 attempts are 404 with identical bodies.
- [ ] The restart test shows the limit still applied after a restart; the concurrency test lets exactly 20 of 30 through.
- [ ] Contract validation passes on every lesson route and fails on a renamed field.
- [ ] Re-seeding keeps old attempts and their versions.
- [ ] `npm run walk -- --lessons` passes and `--lessons --keyboard` passes with 0 mouse clicks; the accessibility-tree check passes and fails on a deliberately unnamed button (negative, then revert).
- [ ] No lesson page text contains score, rank, points or level.
- [ ] The benchmark note exists with p50, p95 and max and says what it does not show.
- [ ] Standing invariants: idempotency, reconciliation (progress counts versus rows), reproducibility (a fingerprint of the six lessons' content hash is stored and unchanged after a second seed).

## Out of scope
- Load testing with many users, screen-reader testing (08_01), new lessons.

## Notes for the implementer
A failed check is a finding. Fix the cause in the lowest layer that owns it and keep the failing case as a regression test. Write down each scan exemption and test it.
