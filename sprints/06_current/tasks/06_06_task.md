# Task 06_06: NestJS `app` schema, learners and login

**Sprint:** 06     **Depends on:** 06_01     **Size:** M
**Concepts to read first:** [06_07](../concepts/06_07_two-backends-one-contract-nestjs-gateway-and-python-analytics.md)

## Goal
NestJS owns a new database schema `app`, migrated by its own tool, and can register a learner, log them in and identify them from a token, with passwords stored only as slow salted hashes.

## Context
Blueprint Section 24 (database ownership rule: `app` is owned and migrated by NestJS) and 15 (security basics). Learner accounts separate people on one machine; they are not a public sign-up system.

## What to do
1. Set up `node-pg-migrate` for the gateway: SQL migration files in `apps/api/migrations/`, version table `app.pgmigrations`, the command `npm run migrate:up|down`, using `DATABASE_URL`. The schema `app` is created by the first migration (`CREATE SCHEMA app`).
2. Migrations (each with a working `down`):
   - `app.learner(learner_id uuid PK default gen_random_uuid(), display_name text NOT NULL, display_name_key text NOT NULL UNIQUE` (lower-cased, trimmed copy used for uniqueness)`, password_hash text NOT NULL, created_at timestamptz default now(), last_login_at timestamptz)` with CHECK on `char_length(display_name) BETWEEN 2 AND 40`.
   - `app.learner_episode(learner_id uuid FK -> app.learner ON DELETE CASCADE, episode_id text NOT NULL, created_at timestamptz default now(), PRIMARY KEY (learner_id, episode_id), UNIQUE (episode_id))` (an episode has one owner; `episode_id` is a Python-owned id, so it is a plain text column, not a foreign key across schemas).
   - `app.glossary_term` is created in 06_07; do not add it here.
3. Auth module: `POST /auth/register` (`display_name`, `password`), `POST /auth/login`, `GET /me` (guarded). Validation: name 2 to 40 characters, password 10 to 128 characters; a clear plain-language message for each rule.
4. Password hashing with `crypto.scrypt` (`node:crypto`), per-password random 16-byte salt, parameters N = 2^17, r = 8, p = 1 (OWASP's minimum for scrypt; set `maxmem` high enough, Node's default limit is too low for these parameters), stored as a self-describing string `scrypt$N$r$p$salt$hash` so parameters can be raised later; compare with `timingSafeEqual`. Wrong name and wrong password give the same message and status (401, "That name or password is not right").
5. JWT: signed with `JWT_SECRET`, claims `sub` (learner id) and `exp` (8 hours); an `AuthGuard` that reads `Authorization: Bearer ...`; missing, malformed, expired or tampered tokens give 401. A decorator `@CurrentLearner()` for handlers.
6. Throttling: login and register limited to 5 attempts per minute per client address and name (use `@nestjs/throttler`), answer 429 with a plain message.
7. Logging: never log request bodies of the auth routes, passwords, hashes or tokens (test below).
8. Swagger: document the three routes with examples (no real credentials), bearer-auth scheme; refresh `docs/02-domain/openapi-gateway.json`.
9. Update `docs/02-domain/data-dictionary.md` with `app.learner` and `app.learner_episode` and the ownership note.

## Where to do it
- Folder / file: `apps/api/migrations/`, `apps/api/src/auth/`, `apps/api/src/db/`, `docs/02-domain/data-dictionary.md`.
- Technology: NestJS, `pg`, `node-pg-migrate`, `node:crypto`, `@nestjs/jwt`, `@nestjs/throttler`, Vitest + Supertest.

## Inputs
- 06_01 scaffold; the throwaway database `marketlab_test` for tests (tests touch only `app.*`).

## Deliverables
- Migrations, auth module, guard, tests, dictionary update, refreshed OpenAPI.

## Acceptance criteria / tests
- [ ] Migrations: up, down, up leaves the same table list in `app`; the version table is `app.pgmigrations`; after `down` the schema `app` is gone and the Python tables are untouched (compare the `market` and `research` table lists before and after).
- [ ] Register then login returns a token; `GET /me` with it returns the display name and no password material; the stored value starts with `scrypt$131072$8$1$` and differs for two learners with the same password (salt).
- [ ] Negative tests: wrong password and unknown name give identical status and message; duplicate names differing only by case or surrounding spaces are rejected (409); 9-character password and 129-character password rejected (422); name of one character rejected.
- [ ] Guard negative tests: no header, `Bearer garbage`, a token signed with another secret, a token with a past `exp` all give 401 on `GET /me`.
- [ ] Throttle: the 6th login in a minute from one client gets 429.
- [ ] Log scan (negative): run register/login/me with a distinctive password `Sup3r-Secret-Pw-123`; the captured logs and every response body contain neither the password nor the hash nor the token value (except the login response, which contains the token by design).
- [ ] Timing: hashing takes between 50 ms and 2 s on this machine (record the measured value; do not state a target as achieved before measuring).
- [ ] Structural test: no file under `services/market-data/src` contains SQL that writes `app.` tables.
- [ ] Standing invariants: idempotency (running `migrate:up` twice changes nothing), reproducibility.

## Out of scope
- Password reset, email, OAuth, roles, refresh tokens, deleting accounts, sign-up for other people.

## Notes for the implementer
Keep the error messages friendly and short (they are shown to beginners). Do not invent a second password rule on the client that differs from these.
