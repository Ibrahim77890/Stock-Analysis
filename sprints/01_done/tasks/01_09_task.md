# Task 01_09: Range-query function and the first PostgreSQL scale benchmark

**Sprint:** 01     **Depends on:** 01_06, 01_07     **Size:** M
**Concepts to read first:** [01_07 Postgres schema](../concepts/01_07_postgres-time-series-schema-and-indexing.md), [01_08 Benchmarking](../concepts/01_08_benchmarking-methodology.md)

## Goal
A tested function that returns raw bars for a symbol and date range, and a reproducible benchmark showing how this query behaves at 12.6 million rows in PostgreSQL.

## Context
Blueprint Week 3 and Section 13. This produces the first evidence for or against "PostgreSQL alone is enough" (blueprint 24).

## What to do
1. Implement `get_bars(symbol, start, end, source='alpaca')` in a `read` module. It returns a DataFrame ordered by date, validates `start <= end`, and returns an empty frame for unknown ranges (but raises for an unknown symbol).
2. Make the signature ready for the replay requirement: give it an optional `as_of` (or `max_date`) argument that caps the returned dates; document that this will become the replay cursor. Test: with `max_date=D`, no row has `trade_date > D`.
3. Write a seeded synthetic generator: geometric random walk, valid OHLC, positive prices, integer volume, 5,000 synthetic symbols x 2,520 sessions (~12.6M rows). Output Parquet to the data folder (not committed). The seed and parameters are in the benchmark report.
4. Load the synthetic data into a **separate** schema or database (e.g. `bench`) using the same table definition, via `COPY`. Do not mix it with real data.
5. Write the benchmark script: for each of these workloads run 200 random queries after 20 warm-up queries and report p50/p95/p99 and mean:
   - W1: one symbol, one year of daily bars.
   - W2: one symbol, full history.
   - W3: all symbols, a single date (cross-section).
   - W4: 20 symbols, 1 year (IN list).
6. For W1 and W3 save `EXPLAIN (ANALYZE, BUFFERS)` output and state whether an index was used.
7. Measure load throughput (rows/s), table size, and index size (`pg_total_relation_size`, `pg_relation_size`).
8. Run once with a cold cache (restart the container, drop OS cache if you can) and once warm; report both.
9. Write `benchmark-01-postgres-daily-bars.md`: hardware (CPU, RAM, disk), OS, PostgreSQL version and non-default settings, dataset description, results table, EXPLAIN excerpts, and a plain-language conclusion including what you would test next.

## Where to do it
- Folder / file: Python code folder (`read` module, `bench` scripts); report in the benchmarks docs folder.
- Technology: Python, Polars, NumPy (seeded `Generator`), psycopg, PostgreSQL.

## Inputs
Schema from 01_06; real loaded data for correctness tests.

## Deliverables
- `get_bars`, generator, benchmark script, benchmark report.

## Acceptance criteria / tests
- [ ] `get_bars` returns exactly the rows expected for AAPL 2020-08-25..2020-09-04 (compare with the raw file).
- [ ] `max_date` boundary test never returns a later date (property test with 100 random cutoffs).
- [ ] Generator test: same seed -> identical output hash; every row satisfies the OHLC rules.
- [ ] Benchmark script prints environment info and writes the report automatically; a second person can reproduce with the documented commands.
- [ ] Report states numbers measured on your machine only; no claims without a table row.
- [ ] Decision recorded: is partitioning or BRIN justified by the measurements? (Answer yes/no with evidence.)

## Benchmark
This task *is* the benchmark. Metrics: load rows/s, query p50/p95/p99 for W1-W4 (cold and warm), table/index size.

## Out of scope
DuckDB/ClickHouse comparison (later sprint), the 100M-row trade benchmark, concurrency tests.
