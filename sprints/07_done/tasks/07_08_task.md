# Task 07_08: Cross-layer checks for the Lab: leaks, isolation, limits, contract, speed, real browser

**Sprint:** 07     **Depends on:** 07_04, 07_07, 07_01     **Size:** L
**Concepts to read first:** [07_03](../concepts/07_03_the-vault-out-of-sample-holdout-and-one-use-tests.md), [07_05](../concepts/07_05_protecting-expensive-endpoints.md), [07_06](../concepts/07_06_explaining-performance-numbers-and-charts-to-beginners.md)

## Goal
Show, on the real three-service stack and the real database, that the Lab hides the vault, isolates learners, enforces its limits, matches its contracts, is fast enough to feel interactive, and works for a person using a browser.

## Context
Sprint 06 proved the same properties for the learning loop (leak fuzz, isolation, latency, browser walk). The Lab adds a hidden window that must stay hidden, and an expensive endpoint that must stay bounded.

## What to do
1. **Vault leak fuzz (real stack):** for 5 symbols and 40 random rules each, call every Lab route before the vault is opened and scan every response (bodies, error bodies, headers) for any date after the study's practice end, any vault metric key, and the vault bar count combined with dates. Also run the same scan on the web pages' text via the browser walk. Exempt nothing except the learner's own `created_at`.
2. **Data-change test:** for one study, truncate a copy of the market data after the practice end (a scratch database, not the real one), run 10 rules in both databases, and require byte-identical Python results (practice results cannot depend on vault data).
3. **Isolation fuzz (real stack):** two learners, 200 random cross-access attempts on study routes; all 404/401 with identical bodies; the Python request log shows no call for them.
4. **Limits on the real stack:** each cap from 07_02 to 07_04 returns its status; the 21st run in a minute returns 429; the 21st study returns 422; a second vault returns 409; each rejected call leaves the database counts unchanged.
5. **Time and size caps:** run the largest allowed input (slow = 300, 200 paths) through the gateway and record the time; the response size is under 150 KB; a 30 s timeout is exercised with a fake slow Python (504 with a plain message).
6. **Contract validation:** validate real responses of every Lab route against the gateway OpenAPI (Ajv, as in Sprint 06) and the Python OpenAPI; both pass; a deliberate field rename fails (negative test).
7. **Latency benchmark** (`apps/api/scripts/latency.ts` extended, interleaved): p50/p95/max over 30 calls for `GET /lab/studies/:id`, a typical run (slow = 50, 100 paths), the largest run, direct versus through the gateway. Record machine details; write `docs/03-benchmarks/benchmark-03-lab-run-latency.md`. No target before measuring; if the typical run exceeds 5 seconds at p95 write it as a finding and a pending item rather than weakening the test.
8. **Reproducibility:** a fingerprint script `scripts/reports/lab_fingerprint.py` runs 5 symbols x 4 rules and prints a hash of all results; running it twice and on a freshly built database (07_09) gives the same hash.
9. **Browser walk of the Lab** (extend `apps/web/scripts/walk.mjs` from 07_01 with a `--lab` flag): sign up, start a study, run two rules, read the cards, open the vault with the confirmation, and check the opened view; keyboard-only variant (`--lab --keyboard`) for the form and the confirmation dialog; accessibility-tree assertions on the study page (names for all controls; chart has a table alternative). Screenshots under `data/reports/walk/`.
10. Remove or list as an orphan every study created by the checks that is not needed (counts in the note), as in Sprint 06.

## Where to do it
- Folder / file: `apps/api/test/lab-e2e.spec.ts`, `apps/api/scripts/latency.ts`, `services/market-data/scripts/reports/lab_fingerprint.py`, `apps/web/scripts/walk.mjs`, `docs/03-benchmarks/`.
- Technology: Vitest, Ajv, puppeteer-core, Python.
- Database schema/ownership: the real database for the stack checks; a scratch database for the data-change test (dropped afterwards).

## Inputs
- The running stack, 07_01 walk script, Lab implementation.

## Deliverables
- Tests and scripts, benchmark note, fingerprint, completion note with counts and measured numbers.

## Acceptance criteria / tests
- [ ] Leak fuzz: 200 runs and zero findings; a planted leak (a fake Python field with `practice_end` forwarded by a deliberately broken whitelist in a test build) is detected by the same scan (negative test).
- [ ] Data-change test: 10 of 10 results byte-identical between the full and the truncated databases.
- [ ] Isolation fuzz: 200 of 200 are 404/401 with identical bodies and zero Python calls; owners get 200.
- [ ] Every cap returns the expected status and leaves counts unchanged.
- [ ] Largest run time, response size and the timeout path are measured and recorded.
- [ ] Contract validation passes on every Lab route; the rename negative test fails as expected.
- [ ] Benchmark note exists with machine details, p50/p95/max, and a plain statement of what it does not show (single machine, warm caches).
- [ ] Fingerprint is identical across two runs.
- [ ] The Lab browser walk passes, with and without `--keyboard`; the number of mouse clicks in keyboard mode is 0.
- [ ] Orphan studies and test learners from checks are counted in the note.
- [ ] Standing invariants: causality and replay boundary (fuzz, truncation), idempotency (repeat runs), reproducibility (fingerprint), reconciliation (study counts).

## Out of scope
- Load testing with many users, cloud deployment, screen-reader testing (listed in `pending/` if not done in 07_01).

## Notes for the implementer
A failed check is a finding. Fix the cause in the lowest layer that owns it, and keep the failing case as a regression test.
