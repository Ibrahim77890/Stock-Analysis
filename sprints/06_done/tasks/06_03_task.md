# Task 06_03: Precommitted predictions, append-only, resolved from later bars

**Sprint:** 06     **Depends on:** 06_02     **Size:** M
**Concepts to read first:** [06_05](../concepts/06_05_precommitment-append-only-records-and-resolving-outcomes.md), [06_02](../concepts/06_02_probability-forecasts-proper-scoring-and-brier-score.md)

## Goal
A learner can store a probability forecast at the current cursor of an open episode; the record can never be edited, and its outcome is filled in exactly once, from bars that arrived later.

## Context
Blueprint 23.2 (prediction scoring). The score is meaningless unless predictions are committed before the outcome exists and cannot be changed.

## What to do
1. Migration `0011` (create `research.prediction`): `prediction_id bigint identity PK`, `episode_id text FK -> research.episode ON DELETE RESTRICT`, `made_at int` (cursor position when made), `horizon int CHECK (horizon IN (1,5,10))`, `p_up numeric(5,4) CHECK (p_up BETWEEN 0.01 AND 0.99)`, `created_at timestamptz default now()`, `outcome smallint NULL CHECK (outcome IN (0,1))`, `status text CHECK (status IN ('pending','resolved','void'))`, `resolved_at_pos int NULL`, `UNIQUE (episode_id, made_at, horizon)`. Up, down, up.
2. In the same migration add a PL/pgSQL `BEFORE UPDATE OR DELETE` trigger: `DELETE` always raises; `UPDATE` is allowed only when `OLD.status = 'pending'`, `NEW.status IN ('resolved','void')`, and `episode_id, made_at, horizon, p_up, created_at` are unchanged; a resolved or void row can never change again.
3. Extend `episode.py` (still the only module with SQL on these tables):
   - `add_prediction(conn, episode_id, horizon, p_up)`: uses the **server's** `cursor_pos` as `made_at` (the client cannot send it); rejects a revealed episode (409), `made_at + horizon > n_bars` (422, the resolving bar would not exist), invalid `p_up` or `horizon` (422); a repeat of the same `(episode, made_at, horizon)` returns the existing record unchanged with `created = false` (idempotent).
   - Resolution inside `advance_episode`, in the same transaction: for every pending prediction with `made_at + horizon <= new cursor_pos`, set `outcome = 1` if `close[made_at + horizon] > close[made_at]` else 0 (strictly greater; ties are 0), `status = 'resolved'`, `resolved_at_pos`. Closes are read only from positions <= the new cursor.
   - `reveal` (used by 06_05) sets still-pending predictions to `void`.
   - `list_predictions(conn, episode_id)`: id, `made_at` (as day), horizon, `p_up`, status, outcome (outcome shown only when resolved).
4. Endpoints in the Learning router: `POST /episodes/{id}/predictions` (body `horizon`, `p_up`), `GET /episodes/{id}/predictions`.
5. Tests as below, including a direct-SQL attempt to edit and delete.

## Acceptance criteria / tests
- [ ] Migration up/down/up; `alembic heads` shows `0011`; the trigger exists after `up` and the table list after `down` matches the previous state.
- [ ] Direct SQL negative tests: `UPDATE research.prediction SET p_up = 0.5`, changing `horizon` or `made_at`, re-resolving a resolved row, and any `DELETE` all raise; setting `outcome`/`status` on a pending row succeeds exactly once.
- [ ] A prediction made at position 60 with horizon 5 stays pending after advancing to 64 and resolves on advancing to 65 with the hand-computed outcome (synthetic episode with a known seed; compare against a manual comparison of two closes).
- [ ] **Replay boundary:** during resolution no query reads a position beyond the new cursor (test by recording the highest position read, or by running on a copy truncated at the cursor and getting the same outcomes); fuzz 50 random advance sequences.
- [ ] Idempotency: submitting the same prediction twice returns one row and `created = false` the second time; different horizons at the same position are separate rows.
- [ ] Rejections: horizon not in {1,5,10}, `p_up` of 0, 1, 0.005 or 0.995 (422); a prediction whose resolving bar lies beyond `n_bars` (422); on a revealed episode (409); unknown episode (404).
- [ ] Reveal marks pending predictions void; reconciliation `resolved + void + pending = total` holds in every state (test after random sequences).
- [ ] Ties: equal closes give outcome 0 (test with a crafted synthetic frame).
- [ ] Standing invariants: idempotency, replay boundary, reconciliation.

## Out of scope
- Scoring (06_04), score endpoint and reveal endpoint (06_05), editing or withdrawing a prediction (deliberately impossible).

## Notes for the implementer
Do not let the client send `made_at`. Write the resolution query so that the bar positions are bounded by a parameter equal to the new cursor, and test that bound directly.
