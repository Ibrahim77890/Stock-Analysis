# Task 06_11: "Under the hood": see how the system works and what it is doing right now

**Sprint:** 06     **Depends on:** 06_10     **Size:** M
**Concepts to read first:** [06_08](../concepts/06_08_designing-for-novices-plain-language-and-a-light-theme.md), [06_07](../concepts/06_07_two-backends-one-contract-nestjs-gateway-and-python-analytics.md)

## Goal
A learner (and the project owner) can open one page that shows, in plain words and a diagram, how MarketLab is built, whether each part is running, what the server is hiding or keeping for the current episode, and what happened on each of their recent requests.

## Context
The owner asked for more visibility to understand the system. This also serves blueprint 23.2 (data lineage panel, "reinforces the data-engineering story") and the product principle of not hiding how results are produced.

## What to do
1. **How it works** section: an SVG diagram with four boxes and arrows: Your browser -> NestJS "front desk" (logins, who owns what) -> Python "number cruncher" (data, scores) -> PostgreSQL (three drawers: `app`, `research`, `market`). Under each box one or two plain sentences and who owns which database drawer. The diagram has a text alternative (a numbered list of the same steps).
2. **Live status** strip from `GET /system`: three lights with words ("Front desk: running", "Number cruncher: running", "Database: running"), each with the last check time; if something is down, one sentence says what that means for the learner ("You can look at old results but cannot start a new episode").
3. **What the server knows about this episode** (for the open episode): two columns. "Hidden from you until the reveal": name, dates, price level, real or made-up. "Kept by the server": your guesses (number, and that they cannot be edited), the current day, the random seed (shown only after reveal). Each hidden item has a one-line reason.
4. **My recent requests** table from `GET /trace`: time, what you did in words (a fixed map from route pattern to sentence, for example "Moved the episode forward"), which parts handled it (browser -> front desk -> number cruncher), how long it took, and a status word ("worked", "refused: not yours", "failed: try again"). No bodies, tokens or identifiers are shown. A "Show more" row explains the route pattern and status code for curious users.
5. **Where the numbers come from:** after a reveal of a real episode, a "Data trail" block (reuse the component from 06_10) with the plain sentence for each step: downloaded from the provider, checked, stored, adjusted for splits as of the last day you saw, shown with name and dates hidden.
6. **For the owner:** a collapsed "System map" with the ownership table from `GET /system` (which service owns which schema), migration names, ports, and the links to Swagger for the gateway and for Python (loopback addresses), labelled "for developers".
7. All text passes the copy check; terms use the `Term` component.

## Where to do it
- Folder / file: `apps/web/src/pages/UnderTheHood.tsx` and components `ArchitectureDiagram`, `StatusLights`, `WhatTheServerKnows`, `RequestTable`, `SystemMap`; copy in `src/copy/hood.ts`.
- Technology: React, TypeScript, SVG.
- Database schema/ownership: none (reads `GET /system`, `GET /trace`).

## Inputs
- 06_07 endpoints `/system` and `/trace`; 06_10 `DataTrail` component.

## Deliverables
- The visibility page with tests and a link "How does this work?" in the top bar and on the episode screen.

## Acceptance criteria / tests
- [ ] Component tests (API mocked): lights show running/down with the right sentence; the diagram has its text alternative and four boxes; the hidden/kept lists change after the reveal (identity moves to a "Now revealed" list).
- [ ] The request table shows only words, durations and statuses: a mocked trace entry containing a bearer token, a body and a concrete episode id in extra fields is not rendered (negative test: scan the DOM).
- [ ] A refused request (404 for someone else's id) is shown as "refused: not yours" without naming the id.
- [ ] Reading ease of the page copy is 60 or more; no sentence over 25 words.
- [ ] Accessibility checks: table headers, labelled status lights (text not colour only), keyboard reachable "Show more" controls.
- [ ] Manual check recorded: with all three services running, the lights are green; stop the Python service and observe the page explaining what stopped; start it again.
- [ ] `npm run build`, `npm test`, `npm run check:api`, `npm run check:copy` pass.
- [ ] Standing invariant: replay boundary (the page shows no data beyond the cursor and no identity before the reveal).

## Out of scope
- Editing configuration from the page, metrics dashboards, log viewers, anything beyond the learner's own requests.

## Notes for the implementer
The page explains the system; it must not weaken it. Everything shown must come from endpoints that already enforce ownership and redaction.
